================================================================================
0. PROPÓSITO Y ALCANCE
================================================================================
El repositorio contiene un sistema completo de una franquicia de bubble tea
("Bubble Drink"). Son TRES aplicaciones web monorepo que comparten la MISMA base
de datos SQLite:

  - apps/store   -> Tienda pública (kiosco/totem con PWA, Next.js puerto 3000).
  - apps/cajero  -> App del cajero (pantalla táctil para registrar pedidos y
                    cobrar, Next.js puerto 3002).
  - apps/admin   -> Panel de administración (Next.js puerto 3001). ES EL OBJETO
                    DE ESTE DOCUMENTO.

El admin NO registra pedidos: los pedidos los crea la app CAJERO. El admin los
visualiza, los acepta/cobra, los entrega, los anula, les aplica descuentos,
reimprime comandas, gestiona el catálogo de bebidas y precios, configura el QR
de pago, administra el carrusel de imágenes de la tienda, la impresora térmica,
los usuarios y consulta 9 tipos de reportes.

IMPORTANTE — DISCREPANCIA EN EL STACK:
En versiones previas de este documento se listó PostgreSQL como base de datos.
La REALIDAD DEL CÓDIGO es que Prisma usa `provider = "sqlite"` con
DATABASE_URL="file:./dev.db". El proyecto corre íntegramente con SQLite local
(archivo en packages/db/prisma/dev.db). Si se reconstruye, respetar SQLite o
migrar explícitamente (ver sección 10).

1. STACK, APARIENCIA Y ESTÉTICA
================================================================================
STACK REAL
  - Next.js 15.1 (App Router, server + client components), React 19, React DOM 19.
  - TypeScript 5.6 (strict mode por defecto de Next).
  - Tailwind CSS 3.4 + preset propio en `@bubba/config` (colores basados en CSS
    variables HSL de shadcn/ui).
  - Prisma 6 (`@prisma/client`) sobre SQLite.
  - NextAuth 4.24 (estrategia JWT, provider Credentials con bcryptjs).
  - zod 4.4 para validación de parámetros de reportes.
  - jspdf + html2canvas para exportar PDF (cliente). xlsx (SheetJS) para Excel
    (cliente). lucide-react para iconos.
  - Monorepo pnpm workspaces con scripts `-r` (turbo para lint/typecheck).

APARIENCIA Y ESTÉTICA (LO QUE SE VE EN PANTALLA)
  - Tema OSCURO FIJO y SEMÁNTICO. No hay toggle de tema ni ThemeProvider.
  - El CSS global define las variables en `:root` (no `dark:`); el `body` usa
    `bg-background text-foreground`. Paleta acordeño:
      background  = slate muy oscuro (hsl 222.2 47.4% 11.2%)
      card        = casi negro azulado (hsl 222.2 84% 4.9%)
      primary     = azul (hsl 221.2 83.2% 53.3%) con texto blanco
      secondary   = gris azulado medio (215.3 19.3% 30.4%) con texto blanco
      muted       = 217.2 32.6% 17.5% (fondo sutil), muted-foreground 65%
      accent      = igual que muted
      border/input= mismo tono que muted
      ring        = primary
      success     = verde (160.1 84.1% 39.4%)
      warning     = ámbar (32.1 94.6% 43.7%)
      destructive = rojo (346.8 77.2% 49.8%)   <-- acciones destructivas
  - Los estilos semánticos de ACCIÓN (fuertes) que el dueño del negocio quiere:
      SUCCESS = verde esmeralda, TEXTO BLANCO.
      WARNING = ámbar, TEXTO BLANCO.
      DESTRUCTIVE = rojo, TEXTO BLANCO.
    El preset de Tailwind NO mapea `success`/`warning` (el Badge los hardcodea,
    ver sección 5). El token `destructive` viene del preset.
  - Como `destructive` ya produce texto blanco sobre rojo, el patrón de botón
    para acciones peligrosas es: `<Button variant="destructive">`.
  - El layout del dashboard es: header con logo + nombre "Bubba Admin", nav
    horizontal (Dashboard, Menú, Carrusel, Pedidos, Pagos, Reportes,
    Impresora, Usuarios), nombre de usuario y botón "Salir"; contenido centrado
    en contenedor `max-w-6xl`.
  - Tipografía: font-sans (sistema). No hay fuentes personalizadas en admin.
  - Idioma de UI: español. Moneda: bolivianos "XX Bs". Fechas formateadas con
    locale "es-MX" (y en impresiones "es-BO").

3. ESQUEMA DE LA BASE DE DATOS (Prisma/SQLite)
================================================================================
Datasource: provider "sqlite", url = env("DATABASE_URL")  [= file:./dev.db].
Generador: prisma-client-js.
Archivo BD: packages/db/prisma/dev.db (única BD compartida por las 3 apps).

MODELOS (nombres de campos exactos):

1) User
   id        String  @id @default(cuid())
   email     String  @unique
   name      String
   password  String              (hash bcrypt, 10 rounds)
   role      Role    @default(CAJERO)
   active    Boolean @default(true)
   createdAt DateTime @default(now())
   orders    Order[]
   -> Relación con Order (userId opcional): el usuario que aceptó/entregó/
      anuló/descontó el pedido.

2) Size  (tamaño de vaso)
   id, name (unique), oz Int, available Boolean @default(true), createdAt,
   drinkPrices DrinkPrice[]

3) Flavor
   id, name (unique), categories FlavorCategoryLink[], available, createdAt

4) FlavorCategoryLink
   id, flavorId -> Flavor (onDelete: Cascade), category FlavorCategory, createdAt
   @@unique([flavorId, category])
   -> Un sabor puede pertenecer a varias categorías (MILK/WATER/SPECIAL).

5) BobaType
   id, name (unique), kind BobaKind, available, createdAt, drinkPrices[]

6) DrinkPrice  (matriz de precios)
   id, category FlavorCategory, sizeId -> Size (Cascade), bobaTypeId -> BobaType
   (Cascade), price Int, createdAt
   @@unique([category, sizeId, bobaTypeId])
   -> Para cada categoría × tamaño × tipo de boba hay un precio exacto (Bs).

7) Topping
   id, name (unique), price Int, available, createdAt

8) Order
   id            String @id cuid
   seq           Int?   @unique         <- número consecutivo del pedido visible
                                        ("Pedido #00001"); lo genera el cajero
   status        OrderStatus @default(RECIBIDO)
   customerName  String?               <- nombre del cliente (mesa/llevar)
   deliveryType  DeliveryType?         <- MESA | LLEVAR (nuevo, 2026-08-26)
   total         Int                   <- total en Bs (enteros)
   createdAt     DateTime @default(now())
   paidAt        DateTime?
   deliveredAt   DateTime?
   userId        String? -> User      <- quién cobró/entregó (IK del cajero)
   paymentMethod  PaymentMethod?
   paymentMethod2 PaymentMethod?
   paymentAmount2 Int?                <- monto del 2º método (pago dividido)
   discountAmount Int @default(0)
   discountReason String?
   discountedAt   DateTime?
   cancelledAt    DateTime?
   cancelReason   String?
   items          OrderItem[]
   @@index([createdAt, status])
   @@index([deliveredAt])
   @@index([userId, status])

9) OrderItem   (una bebida dentro de un pedido)
   id, orderId -> Order (Cascade)
   sizeName String, flavorName String, flavorCategory FlavorCategory,
   bobaTypeName String, unitPrice Int, quantity Int,
   toppings OrderItemTopping[]
   @@index([orderId])
   -> Se guardan los NOMBRES por valor (no FKs). Precio unitario congelado.

10) OrderItemTopping
   id, orderItemId -> OrderItem (Cascade), toppingName String, unitPrice Int

11) PaymentConfig
   id        String @id @default("default")   <- fila única
   qrImage   String    (data URI base64, ej. data:image/png;base64,....)
   mimeType  String
   updatedAt DateTime @updatedAt

ENUMS
  FlavorCategory: MILK | WATER | SPECIAL   (Con leche / Con agua / Especiales)
  BobaKind:       TAPIOCA | POPPING        (Tapioca / Explosivas)
  OrderStatus:    RECIBIDO | ACEPTADO | ENTREGADO | ANULADO
  Role:           ADMIN | CAJERO
  PaymentMethod:  EFECTIVO | QR | TARJETA
  DeliveryType:   MESA | LLEVAR

4. RUTAS Y PÁGINAS DE LA APP ADMIN (CON PORTAVOZ DE COMPORTAMIENTO)
================================================================================
AUTENTICACIÓN Y PROTECCIÓN
  - NextAuth v4 con estrategia JWT y provider Credentials. authorize() busca
    el usuario por email (exacto), compara bcrypt, y REVISA user.active:
    si está desactivada NO puede iniciar sesión. Devuelve {id,email,name,role}.
  - Callbacks jwt/session copian id y role al token y a session.user.
    session.user.role también se usa en app - default "CAJERO" si faltase.
  - pages.signIn = "/login".
  - middleware.ts (raíz de apps/admin) usa withAuth con authorized() que
    devuelve true SOLO si token.role === ADMIN (default CAJERO si no hay token).
    Matcher: "/((?!login|api/auth|api/reports|_next/static|_next/image|favicon.ico).*)"
    => Casi todas las rutas exigen ADMIN y redirigen a /login si no.
    NOTA: api/reports está EXCLUIDO del middleware (las API se protegen solas
    con requireSession → 401 JSON). api/slideshow y api/printer NO están
    excluidas → dependen del redirect del middleware (deuda, sección 10).
  - (dashboard)/layout.tsx: lee sesión y redirige a /login si no hay usuario.
    Encapsula AdminNav y el contenedor max-w-6xl.
  - app/api/auth/[...nextauth]/route.ts exporta NextAuth(authOptions) como
    GET/POST.

PÁGINAS (ruta -> comportamiento):

/ (Dashboard) — SERVER
  - 3 métricas del DÍA (hora local del servidor, setHours(0,0,0,0)):
      "Pedidos hoy":       count orders createdAt >= hoy
      "Pedidos por cobrar":count orders status=RECIBIDO
      "Ventas del día":    SUM total de órdenes creadas hoy
  - "Pedidos recientes": últimos 5 pedidos (include items), con #pedido
    (formatOrderCode = seq padStart 5 ceros), cantidad de bebidas, hora,
    Badge de estado y total.
  - statusVariant: RECIBIDO->warning, ACEPTADO->default, ENTREGADO->success,
    ANULADO->destructive.
  - Nota de deuda: usa medianoche LOCAL del servidor, NO America/La_Paz (a
    diferencia de los reportes). Si el servidor está en otra zona horaria, el
    dashboard puede no coincidir con los reportes diarios.

/login — page.tsx (server) + login-form.tsx (cliente)
  - Form centrado (max-w-sm), logo circular "B" gradiente ámbar, título
    "Bubba Admin", campo correo y contraseña, botón "Iniciar sesión".
  - handleSubmit: signIn("credentials", {redirect:false}); si error, llama
    isAccountInactive(email,password) para discriminar mensaje:
      inactiva  -> "Esta cuenta está desactivada. Contacta al administrador."
      credenciales inválidas -> "Credenciales inválidas. Verifica tu correo y
      contraseña."
    Si ok: router.push(callbackUrl || "/") + router.refresh().
  - isAccountInactive (server action) solo revela "inactiva" cuando las
    credenciales SON válidas y la cuenta está desactivada (no filtra usuarios).

/menu — page.tsx (server) + MenuManager (cliente)
  - Carga: sizes (por oz asc), flavors (con sus categories), bobaTypes,
    toppings, drinkPrices (con size/bobaType para precios).
  - Orden en la página:
    1) Tamaños de vaso: crear (nombre + onzas), activar/desactivar (Badge
       Disponible/No disponible + botón), editar (diálogo), eliminar.
    2) Sabores: crear con CategoryToggles (3 categorías), toggle de
       categorías en cada sabor (llama updateFlavor), activar/desactivar,
       editar, eliminar.
    3) Tipos de boba: crear con Select de kind (Tapioca/Explosivas), toggle,
       editar, eliminar.
    4) Toppings: crear (nombre+precio), toggle, editar, eliminar.
    5) Matriz de precios: UNA tabla editable por categoría (SPECIAL, WATER,
       MILK): filas=tamaños, columnas=bobas, celdas Input precio; botón
       "Guardar matriz" → saveDrinkPrices (upsert transaccional).
  - Detalle: los botones destructivos (eliminar) se pintan
    variant="destructive" (rojo). Los toggles de disponible usan Badge
    success/secondary. Ojo: no hay confirmación en eliminar (se elimina
    directo; si falla se muestra error en card roja).

/slideshow — page.tsx (cliente)
  - Carga GET /api/slideshow. Muestra "Tiempo entre fotos" (intervalMs,
    min 1000, step 500, recomendado 3000-5000) y lista de imágenes.
  - Subir: input file multiple oculto; por cada archivo comprime en el
    navegador (createImageBitmap -> resize a max 1600px de ancho -> canvas ->
    JPEG calidad 0.82 con fondo blanco; si el archivo ya es JPEG < 400KB y <=
    1600px se sube tal cual) y hace POST /api/slideshow/upload secuencialmente
    para conservar orden; muestra progreso "Subiendo X de Y".
  - Cada imagen: preview, Input para "alt" (guardado en vivo vía PUT
    /api/slideshow), flechas ↑/↓ para reordenar (PUT), botón 🗑 (DELETE
    /api/slideshow?src=...).
  - mediaUrl: si src empieza con "/images/" lo convierte a
    "/api/slideshow/media/{nombre}" (así el admin puede ver las imágenes que
    sirve la tienda sin acceso directo al public de store).

/orders — page.tsx (server) + OrdersClient (cliente)
  - Lee ?status=. Filtro por tabs (Todos/Recibidos/Aceptados/Entregados/
    Anulados) usando Links con query param. Lista ordenada por createdAt desc,
    include items+toppings, mapea a tipo Order (ISO strings).
  - Card de pedido (OrdersClient):
    - Encabezado: "Pedido #NNNNN", "Para: {customerName}" (si el cliente dio
      nombre), fecha/hora (es-MX), Badge método de pago (si hay: simple o
      "Efectivo + QR" cuando paymentMethod2 existe), Badge estado
      (statusVariant), total en bold.
    - Info de auditoría (si existe): "Pago registrado: ...", "Entregado: ...",
      "Anulado: {motivo} · {fecha}", "Descuento aplicado: −X Bs (motivo)".
    - Items: "N× size · flavor · boba" + toppings anidados (Toppings: ...) y
      total del ítem (unitPrice+toppings)*cantidad.
    - OrderActions (según estado):
        RECIBIDO -> Botón "Registrar pago" (despliega panel: select del
          método EFECTIVO/QR + "Confirmar pago (TOTAL Bs)"), botón
          "Cobro dividido" (abre SplitPaymentDialog).
        ACEPTADO -> Botón verde "Entregar".

API ROUTES (todas en app/api):

/api/auth/[...nextauth]
   GET/POST delegados a NextAuth(authOptions). middleware excluye api/auth.

/api/reports/*  (9 rutas, TODAS GET; todas envuelven con handleReportRoute;
  primero requireSession() -> si no hay sesión: 401 JSON errorBody UNAUTHENTICATED;
  después parsean los query params con zod y assertRange; devuelven
  reportEnvelope {data, meta:{report, from, to, generatedAt, currency:"BOB"}};
  soportan format=csv salvo donde se indique. Monto en Bs enteros.)
  - dashboard-summary: SIN parámetros. Hoy vs ayer (delta % ingresos/pedidos),
    últimos 7 días, pendientes (RECIBIDO). Caché EN MEMORIA 30 seg (module var).
    IMPORTANTE: proyección de "hoy" en America/La_Paz.
  - daily?date=YYYY-MM-DD&format=: ingresos, órdenes, ticket prom., bebidas,
    ingreso toppings, descuentos, anulaciones, breakdown por categoría y por
    método de pago (contabiliza pagos divididos: al método1 va total - monto2,
    al método2 va monto2). CSV con filas por categoría.
  - sales-range?from&to&granularity=(day|week|month)&status&format=: serie por
    bucket (day->YYYY-MM-DD, week->ISO YYYY-Www, month->YYYY-MM), mejor día,
    comparación vs periodo anterior (delta %), agrupable por estado (si se
    pasa status==ANULADO lo deja pasar; si no, excluye anuladas).
  - peak-hours?from&to&weekday(0-6, lun=0)&hourFrom&hourTo: distribuye órdenes
    por hora local (0-23); calcula hora pico y hora más tranquila (solo horas
    con venta dentro de rango).
  - category-sales?from&to&format=: unidades/ingresos por categoría + share %+
    mejor categoría.
  - top-products?from&to&groupBy=(drink|flavor|size|bobaType|topping)&metric=
    (quantity|revenue)&limit&format=: ranking. groupBy=topping calcula desde
    toppings. El client solo expone el toggle Top 10 (limit=10), el resto usa
    defaults del cliente (groupBy=flavor, metric=quantity).
  - slow-movers?from&to&limit(default 10)&includeZero(default true)&toppings&format=:
    universo = matriz de precios vigente (categoría×tamaño×boba) o toppings;
    una fila por combinación (aunque no se vendió); ordena ASC por unidades;
    columna Disponible (boba y size disponibles).
  - staff-performance?from&to&userId&format=: órdenes no anuladas atribuidas al
    usuario (userId, userId viene del cajero/admin que cobró/entregó... según
    acción); suma por usuario: órdenes, recaudado, ticket prom., share %.
    Requiere hasAuditSchema() (501 si no).
  - adjustments?from&to&type=(discount|cancellation|all)&userId&page&format=:
    descuentos y anulaciones en el rango (timestamps discountedAt/cancelledAt);
    por usuario opcional; paginación 50 por página; CSV lista todos los items.
    Requiere hasAuditSchema() (501 si no).

SERVER ACTIONS (app/actions) — todas "use server":

auth.ts
  - isAccountInactive(email,password): bool.

catalog.ts — todas validan sesión (getRequiredSession) y revalidan /menu:
  - createSize/updateSize/deleteSize, createFlavor/updateFlavor/deleteFlavor,
    createBoba/updateBoba/deleteBoba, createTopping/updateTopping/deleteTopping,
    saveDrinkPrices (upsert en transacción; filtra precios inválidos >0).
    Detalle: updateFlavor reemplaza categories con deleteMany+createMany;
    updateSize/updateBoba/updateTopping también togglean available; deleteX usa
    delete directo (si hay referencias en pedidos... los nombre se guardan por
    valor en OrderItem, pero los delete de Size/BobaType con DrinkPrice cascade
    pueden fallar si DrinkPrice los referencia — validar).

orders.ts — acciones del ciclo de vida (todas: getRequiredSession + revalidate
    /orders y /):
  - acceptOrder(orderId, method, method2?, amount2?):
      Método debe estar en AcceptablePayment (EFECTIVO|QR).
      El pedido debe existir y estar en RECIBIDO (no ANULADO).
      Si hay method2: también debe ser EFECTIVO|QR, distinto a method,
      amount2 > 0 y < total. Marca ACEPTADO, paymentMethod(1/2),
      paymentAmount2 truncado a entero, paidAt=now, userId = el de quien cobra
      (order.userId si ya había, si no el session.id).
  - deliverOrder(orderId): solo ACEPTADO o error; marca ENTREGADO,
      deliveredAt = deliveredAt ?? now (una sola vez), userId si faltase.
  - cancelOrder(orderId, reason): motivo obligatorio; no doble anulación;
      ANULADO + cancelledAt + cancelReason + userId del que anula.
  - applyDiscount(orderId, amountBs, reason): motivo obligatorio, amount>0,
      amount < total; total -= amount; discountAmount += amount; discountReason/
      discountedAt; userId.
  - reprintOrder(orderId): requiere impresora configurada; imprime
      formatComanda del pedido; devuelve mensaje "Comanda #NNNNN enviada a X".

payment.ts:
  - savePaymentQr(FormData): exige sesión; file debe ser imagen, no vacío, <=2MB;
      guarda como data URI en PaymentConfig id "default" (upsert).
  - removePaymentQr(): delete donde id="default".
  - getPaymentQr(): devuelve {qrImage,mimeType} | null.

users.ts — todas protegen con requireAdminSession (solo ADMIN):
  - Validaciones: nombre obligatorio, email con regex simple y lowercased,
    contraseña mín 6 (solo en create o si se cambia), rol en
    {ADMIN,CAJERO}. No duplicar email.
  - assertLastAdminProtection(): no puedes desactivar tu propia cuenta ni
    quitarte tu rol ADMIN; no puedes desactivar/quitarle ADMIN al ÚLTIMO admin
    activo del sistema (cuenta otros admins activos).
  - createUser, updateUser (puede actualizar solo nombre/rol y opcional
    newPassword), setUserActive(userId, active). Revalidan /users.

print-report.ts:
  - printSummaryReport(): calcula hoy/ayer/7d/pendientes (America/La_Paz) e
    imprime formatSummaryReport en la impresora configurada.
  - printDailyReport(date?): si date YYYY-MM-DD válida usa esa; si no "hoy";
    calcula cierre (igual que API daily) e imprime formatDailyReport.
  - Ambos requieren: sesión (requireSession) + impresora configurada.

6. LÓGICA DE NEGOCIO CRÍTICA (reglas de oro para no romper la app)
================================================================================
1) CICLO DE PEDIDO:
   RECIBIDO -> (acceptOrder, con pago) -> ACEPTADO -> (deliverOrder) ->
   ENTREGADO. EN CUALQUIER MOMENTO -> ANULADO (con motivo). Los reportes de
   ventas SOLO consideran órdenes NO ANULADAS (notCancelled). El dashboard
   admin muestra "Pedidos por cobrar" = los RECIBIDO (los que el cajero aún
   debe cobrar).
2) TOTAL:
   - total es entero en Bs. unitPrice y topping prices son enteros.
   - El total de un ítem = (basePrice + sumtoppings) × quantity.
   - El descuento se resta del total y suma a discountAmount (nunca deja
     total <= 0).
3) PAGO DIVIDIDO:
   Se persisten paymentMethod (1er método), paymentMethod2 y paymentAmount2
   (monto del 2º). El monto del 1º se INFIERE: total - paymentAmount2. Los
   reportes que desglosan por método usan esa resta (nunca guardan monto1).
   Ambos métodos deben ser EFECTIVO/QR (TARJETA existe en el enum pero NO es
   aceptable en el admin/cajero actual).
4) AUDITORÍA:
   - paidAt al aceptar, deliveredAt al entregar (se conserva el primero),
     discountedAt + discountReason, cancelledAt + cancelReason.
   - userId registra quién cobró/entregó/anuló/descontó (en cobro/entrega se
     respeta el userId ya asignado si existe).
   - Los reportes staff-performance y adjustments dependen de estos campos
     (hasAuditSchema los detecta en runtime por la migración reports_audit_fields).
5) HORA Y FECHAS DE REPORTES:
   TODO internacionalización por zona America/La_Paz (GMT-04, sin DST).
   Utilities en lib/reports/range.ts: getZonedParts, zonedToUtc, dayBounds,
   rangeBounds, addLocalDays, previousPeriodRange, dayKeyOf, monthKeyOf,
   isoWeekKeyOf, hourOfDay, weekdayIndex (lun=0). Limitar rango: MAX_RANGE_DAYS
   = 366 (si no, 422 DATE_RANGE_TOO_LARGE; si from>to, 400 INVALID_DATE_RANGE).
   La app cajero crea pedidos con new Date() (hora real del sistema), y los
   reportes proyectan createdAt a America/La_Paz para agrupar por día.
6) FORMATO DE RESPUESTA DE REPORTES (convención API):
   OK 200: { data, meta: { report, from ISO, to ISO, generatedAt ISO,
   currency:"BOB" } }.
   Error: { error: { code, message } } con status según ERROR_CODES:
       400 INVALID_PARAMETER / MISSING_PARAMETER / INVALID_DATE_RANGE
       401 UNAUTHENTICATED       404 NOT_FOUND
       422 DATE_RANGE_TOO_LARGE  501 NOT_IMPLEMENTED_SCHEMA
       500 INTERNAL_ERROR
   Si el error es de zod → INVALID_PARAMETER con el campo ('param').
7) IMPRESIÓN TÉRMICA (lib/printing.ts):
   - Usa PowerShell ("powershell.exe" -NoProfile -NonInteractive -Command)
     con timeout 15s. printText codifica el texto en base64 UTF-8 para
     evitar problemas de codificación.
   - Papel: busca PaperSize 80mm (300-340 unidades); si no, custom 315x10000;
     márgenes 2. Fuente Consolas bold, calibra el tamaño al ancho (máx 12pt)
     para que la línea más larga quepa.
   - Todo el texto se pasa por toAscii() (quita tildes/ñ) ANTES de imprimir:
     la térmica NO acepta caracteres especiales.
   - Formatos: formatComanda (ancho 30), formatTestPage, formatSummaryReport,
     formatDailyReport. Encabezado común: "BUBBLE DRINK" centrado.
   - listPrinters usa Get-CimInstance Win32_Printer y ordena con la
     predeterminada primero.
   - getPrinterConfig/setPrinterConfig leen/graban apps/store/printing.json.
8) CARRUSEL:
   - La config viva está en apps/store/public/slideshow.json y las imágenes en
     apps/store/public/images. El admin escribe ahí (ruta ../store/public
     relativa a su cwd). La tienda (PWA) lee esas imágenes desde /images/*.
   - intervalMs: velo del carrusel en ms. Alt: descripción.
   - No borra archivos huérfanos si se elimina la entrada del JSON (deuda).
9) QR DE PAGO:
   - Una sola fila (id "default") en PaymentConfig. El cajero lo muestra al
     cobrar por QR. El admin lo actualiza/elimina. Data URI base64 <= 2MB.
10) USUARIOS:
   - Contraseñas hasheadas bcrypt 10 rounds. Mín 6 caracteres.
   - Cuentas inactivas (active=false) no pueden iniciar sesión en ninguna app.
   - Protecciones: no auto-desactivación ni auto-downgrade; al menos un ADMIN
     activo siempre.

10. DEUDA TÉCNICA Y PUNTOS DE ATENCIÓN (para reconstrucción)
================================================================================
1) SQLite vs PostgreSQL: el stack documentado decía PostgreSQL; el código usa
   SQLite (file). Si el negocio crece (concurrencia entre cajero+admin+store),
   migrar a PG. Todas las queries son Prisma compatibles, pero los reportes
   hacen agregaciones en JS (no GROUP BY SQL) — costoso con muchos pedidos.
2) api/slideshow y api/printer NO tienen requireSession propio: dependen del
   middleware (que hace REDIRECT en vez de 401 JSON). Funciona, pero es
   frágil si se reestructura el matcher. api/reports SÍ devuelven 401 JSON.
3) Dashboard del admin: "hoy" usa la medianoche local del SERVIDOR
   (new Date().setHours(0,0,0,0)); los reportes usan America/La_Paz. Puede
   haber desfase si el servidor no está en esa zona.
4) El preset de Tailwind NO define tokens success/warning como colores de
   tailwind; el Badge los hardcodea (bg-emerald-500/bg-amber-500). Cualquier
   otro componente que use "success"/"warning" en clase NO existirá.
5) hasAuditSchema() cachea en memoria por proceso; si la migración se aplica
   en caliente hay que reiniciar el server para que la cache se resetee
   (existe resetAuditSchemaCache() pero no se usa).
6) Pedidos: customerName/deliveryType son nuevos (2026-08-26). El flujo de
   la tienda (store PWA) y del kiosco deben convivir: hay pedidos para mesa
   y para llevar; en el admin se muestra "Para: {cliente}" si hay nombre.
7) Precios: integer Bs, SIN decimales (no hay manejo de centavos en ningún
   lado; el split dialog valida montos enteros? parseInt, así que comporta
   bien solo con enteros).
8) Lint actual del admin pasa (0 errores) con warnings PRE-EXISTENTES en
   slideshow (uso de <img> sin next/image, file input sin label asociado, etc.)
   Tolerables pero pendientes.
9) No hay tests automatizados (ni unit ni e2e). La validación es manual.
10) Secutity: NEXTAUTH_SECRET de ejemplo; cambiar en producción. No hay
    protección CSRF explícita más allá de la de Next server actions.
11) Los scripts de prueba (seed-ui-test.mjs, query-debug.mjs en
    packages/db/scripts) NO están commiteados; regenerar según necesidad.
12) La impresora se configura desde el admin (localhost:3001) y la impresión
    usa PowerShell del sistema donde corre el admin. La config de impresora
    (apps/store/printing.json) es compartida con el cajero (la app cajero
    reimprime usando la misma config).
13) La pestaña "Impresora" vive en admin; la app cajero SOLO reimprime la
    comanda con la impresora ya configurada (en /orders "Reimprimir comanda").
14) El carrusel no elimina archivos de imagen del disco cuando se borra una
    entrada — se acumulan en apps/store/public/images.
15) Formato de precios en pantalla: "X Bs" (sin símbolo de moneda). Códigos
    de pedido: formatOrderCode = padStart(5,"0").
