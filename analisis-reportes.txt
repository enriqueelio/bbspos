========================================================================
ANÁLISIS DEL MÓDULO DE REPORTES — MÓDULO ADMIN (Bubba)
========================================================================
Fecha de análisis: 2026-09-03
Stack: Next.js (App Router) + Prisma (SQLite) + Tailwind.
Arquitectura: Frontend en `apps/admin`, APIs de reportes bajo
`apps/admin/app/api/reports/*`, helpers compartidos en `apps/admin/lib/reports/*`,
formas de datos en `packages/types`, esquema de BD en `packages/db/prisma/schema.prisma`.

La zona horaria del negocio es `America/La_Paz` (no la del servidor).
Toda conversión de fechas pasa por helpers en `apps/admin/lib/reports/range.ts`
para interpretar días/tiempos locales correctamente.

========================================================================
1. RESUMEN ESTRUCTURADO DE LAS MÉTRICAS ACTUALES
========================================================================

La pantalla de Reportes (`reports-client.tsx`) ofrece 9 pestañas, cada una
alimentada por un endpoint distinto. Todas devuelven un "sobre" común:

  { data: T, meta: { report, from, to, generatedAt, currency: "BOB" } }

La moneda es siempre BOB (Bs). Los montos se almacenan como enteros.
Los reportes con rango usan `from` y `to` en formato YYYY-MM-DD (fecha local)
y permiten exportar a CSV/Excel y (Resumen/Cierre diario) imprimir en térmica.

------------------------------------------------------------
1.1 Resumen / Dashboard (reporte "dashboard-summary")
    Endpoint: api/reports/dashboard-summary
------------------------------------------------------------
- Ventas hoy:      suma de `total` de las órdenes NO anuladas cuya
                   `createdAt` cae dentro del día local actual.
- Pedidos hoy:     cantidad de esas órdenes.
- Ticket promedio hoy: ventas_hoy / pedidos_hoy (redondeado).
- Variación vs ayer (delta %): (hoy - ayer)/ayer para ingresos y pedidos.
                   Si ayer es 0 → null.
- Últimos 7 días:  suma de ingresos/pedidos/ticket de los últimos 7 días
                   locales (incluyendo hoy), sin anuladas.
- Pedidos pendientes: count de órdenes con status = "RECIBIDO".

Nota: este endpoint se cachea en memoria 30 s (CACHE_TTL_MS).

------------------------------------------------------------
1.2 Cierre diario (reporte "daily")
    Endpoint: api/reports/daily?date=YYYY-MM-DD
------------------------------------------------------------
Para un día dado (por defecto hoy):
- Ingresos totales: suma de `total` (sin anuladas).
- Órdenes totales y ticket promedio.
- Bebidas vendidas: suma de `quantity` de todos los items.
- Ingreso por toppings: suma(unitPrice de toppings) * quantity.
- Descuentos aplicados: suma de `discountAmount`.
- Anulaciones: count de órdenes ANULADAS de ese día.
- Desglose por método de pago: Efectivo/QR/Tarjeta (+ pagos divididos,
  reparte `total - paymentAmount2` y `paymentAmount2`).
- Desglose por categoría (MILK/WATER/SPECIAL): nº de órdenes (set único de
  orderId), unidades e ingresos por categoría.

------------------------------------------------------------
1.3 Evolución de ventas (reporte "sales-range")
    Endpoint: api/reports/sales-range?from&to&granularity=day|week|month&status
------------------------------------------------------------
- Serie agrupada por día/semana ISO/mes según `granularity`.
  Cada punto: bucket, órdenes, ingresos, ticket promedio.
- Sumarios: ingresos, órdenes, ticket promedio del periodo y "mejor día".
- Variación contra periodo anterior de igual duración (inmediatamente previo)
  solo en ingresos (comparisonPrevPeriod).
- `status` opcional permite filtrar por estado concreto; por defecto excluye
  anuladas.

------------------------------------------------------------
1.4 Horas pico (reporte "peak-hours")
    Endpoint: api/reports/peak-hours?from&to&weekday&hourFrom&hourTo
------------------------------------------------------------
- Cuenta órdenes e ingresos por hora local (0-23) dentro del rango.
- Filtros opcionales: `weekday` (0=lunes..6=domingo) y ventana de horas
  `hourFrom`/`hourTo` (default 11-23).
- Hora pico: la con más órdenes; hora más tranquila CON venta (>0 órdenes),
  ambas dentro de la ventana horaria.

------------------------------------------------------------
1.5 Por categoría (reporte "category-sales")
    Endpoint: api/reports/category-sales?from&to
------------------------------------------------------------
- Por categoría (MILK/WATER/SPECIAL): unidades, ingresos, participación % de
  ingresos y precio promedio por ítem.
- Mejor categoría por ingresos (solo si hay ingresos > 0).
- No incluye topping revenue; solo unitPrice * quantity de items.

------------------------------------------------------------
1.6 Top productos (reporte "top-products")
    Endpoint: api/reports/top-products?from&to&groupBy&metric&limit
------------------------------------------------------------
- `groupBy`: drink (combinación sabor·tamaño·boba), flavor, size, bobaType o
  topping (agrega por topping en items).
- `metric`: quantity | revenue para ordenar.
- `limit` opcional (el cliente limita a 10 con "Top 10").
- Cada fila: rank, key, unitsSold, revenue, unitPriceAvg (revenue/units).

------------------------------------------------------------
1.7 Baja rotación (reporte "slow-movers")
    Endpoint: api/reports/slow-movers?from&to&limit&includeZero&toppings
------------------------------------------------------------
- Universo = matriz de precios vigente (DrinkPrice × Size × BobaType).
- Para cada combinación calcula unidades e ingresos vendidos; los que vendieron
  poco/poco salen primero (ascendente por unidades).
- `includeZero` (default true) incluye combos sin ventas; `limit` default 10.
- `toppings=true` analiza toppings en vez de bebidas (universo = tabla Topping).
- Incluye campo `available` (¿está disponible en el menú?).

------------------------------------------------------------
1.8 Personal (reporte "staff-performance")
    Endpoint: api/reports/staff-performance?from&to&userId
------------------------------------------------------------
- Requiere esquema de auditoría (hasAuditSchema, campo Order.userId).
- Agrupa por usuario: órdenes procesadas, recaudado, ticket promedio y
  participación % sobre el total recaudado del periodo.
- Solo considera órdenes no anuladas; filtra por `userId` si se indica.

------------------------------------------------------------
1.9 Anulaciones y descuentos (reporte "adjustments")
    Endpoint: api/reports/adjustments?from&to&type&userId&page
------------------------------------------------------------
- Requiere esquema de auditoría.
- Lista de eventos: anulaciones (por cancelledAt) y descuentos (por discountedAt)
  dentro del rango, con responsable (canceledBy/discountedBy, fallback user).
- Sumario: nº de descuentos, total descontado, nº de anulaciones e ingreso
  perdido (suma del total de anuladas).
- Paginado (50/page) y exportable a CSV (todos los ítems, no solo la página).

       const res = await fetch(`/api/reports/${endpoint}`, { cache: "no-store" });

       return (await res.json()).data;

           case "sales-range": result = await fetchData(`sales-range?${rangeQuery}`); break;

           case "adjustments": result = await fetchData<AdjustmentsData>(`adjustments?${rangeQuery}`); break;

         if (!cancelled) setFetched({ key: report, payload: result });

3. CONSULTAS A BASE DE DATOS (Prisma) QUE ALIMENTAN LAS PESTAÑAS
------------------------------------------------------------------------

[Regla general] "Ventas" = órdenes con status != ANULADO (notCancelled).
Los rangos se expresan con { gte: <inicio UTC de día>, lt: <fin UTC de día> }
calculados por dayBounds/rangeBounds en la zona America/La_Paz.

MODELOS relevantes (schema.prisma):
  Order { seq, status, total, createdAt, paidAt, deliveredAt, userId,
          paymentMethod, paymentMethod2, paymentAmount2, discountAmount,
          discountReason, discountedAt, discountedById, cancelledAt,
          cancelReason, canceledById, delayNotified, items[] }
  OrderItem { orderId, sizeName, flavorName, flavorCategory, bobaTypeName,
              unitPrice, quantity, toppings[] }
  OrderItemTopping { orderItemId, toppingName, unitPrice }
  DrinkPrice { category, size, bobaType, price }
  Size/BobaType/Topping { name, available }
  User { id, username, name, role }

3.3 sales-range  (api/reports/sales-range/route.ts)

  const bounds = rangeBounds(query.from, query.to);      // [from 00:00, to+1 00:00)
  const prev = previousPeriodRange(query.from, query.to); // periodo previo igual longitud
  const prevBounds = rangeBounds(prev.from, prev.to);

  const [orders, prevRevenueAgg] = await Promise.all([
    prisma.order.findMany({
      where: { createdAt: { gte: bounds.gte, lt: bounds.lt },
        ...(query.status ? { status: query.status } : notCancelled) },
      select: { createdAt: true, total: true },
    }),
    prisma.order.aggregate({
      where: { createdAt: { gte: prevBounds.gte, lt: prevBounds.lt }, ...notCancelled },
      _sum: { total: true },

4. OBSERVACIONES / NOTAS PARA EVALUACIÓN
------------------------------------------------------------------------
- Moneda entera (Bs) sin decimales en BD.
- "Ingresos" de venta siempre excluyen anuladas; los reportes de ajustes
  exponen las anuladas a parte (ingreso perdido).
- Los descuentos se restan del total de la orden en origen; los programas de
  ventas (dashboard/daily) muestran directamente `total`, no
  "ingreso bruto - descuento" por separado.
- staff-performance y adjustments dependen de que existan campos de auditoría
  (Order.userId, canceledBy, discountedBy, discountedAt, cancelledAt) => si la
  migración no está aplicada devuelven 501 NOT_IMPLEMENTED_SCHEMA.
- dashboard-summary tiene cache en memoria de 30 s (no configurable por
  request).
- La zona horaria es fija a America/La_Paz (constante REPORT_TIMEZONE).
- El cliente fija por defecto el rango "Últimos 7 días" (de hoy-6 a hoy) en las
  pestañas que lo requieren; "Cierre diario"/"Resumen" usan el día actual.
