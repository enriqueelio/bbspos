------------------------------------------------------------
1. DESCRIPCION GENERAL
------------------------------------------------------------

El sistema es el módulo "cajero" (punto de venta de mostrador) de una tienda de bebidas Bubble Tea (bubble drink). Permite al personal de mostrador registrar ventas de bebidas, cobrarlas, seguir su preparación hasta la entrega, y consultar un reporte diario de su rendimiento. Todo se agrupa en un monorepo donde existen además un módulo de administración (backoffice) y una tienda web, pero este documento describe exclusivamente la aplicación "cajero", que corre en el puerto 3002.

El flujo principal de una venta tiene tres fases. Primero, en la pestaña "Nueva Venta", el cajero arma un carrito tocando sabores: elige tamaño, tipo de boba, categoría de bebida y extras; el sistema calcula el precio unitario automáticamente a partir de una matriz de precios. Puede poner hasta dos métodos de pago (dividido) y un nombre de cliente opcional, y al confirmar se crea un pedido en estado "Recibido" y se muestra en la cola. Segundo, en la pestaña "Dashboard", el pedido aparece en cola con su número (secuencia), artículos, total y antigüedad; el cajero registra el cobro (Efectivo, QR, o dividido) lo que pasa el pedido a "Aceptado", y luego lo marca como "Entregado" cuando sale. Tercero, en la pestaña "Reporte del día", se ven los KPI del día (ingresos, pedidos entregados, ticket promedio, tiempos) y el rendimiento individual del cajero, que puede imprimirse en ticket o enviarse a Telegram al cierre.

La aplicación usa autenticación exclusiva para el personal: solo usuarios con rol CAJERO o ADMIN pueden entrar. El resto de la lógica (impresión de comandas en impresora térmica de 80mm, alertas por Telegram cuando un pedido se retrasa más de 10 minutos, y el cierre de caja automático) se apoya en la base de datos SQLite del paquete @bbspos/db.

3. MODELO DE DATOS / PRISMA SCHEMA
------------------------------------------------------------

Base: SQLite. Archivo del schema: packages/db/prisma/schema.prisma. Cliente exportado como "prisma" desde @bbspos/db.

TABLAS:

1) USER (empleados)
   - id: string (cuid, PK)
   - email: string unico (inicia sesion)
   - name: string (nombre mostrado)
   - password: string (hash con bcrypt)
   - role: enum (ADMIN | CAJERO), default CAJERO
   - active: boolean default true (cuenta desactivada no puede entrar)
   - createdAt: fecha
   - orders: relacion -> muchos Order

2) SIZE (tamanos de vaso)
   - id: string (cuid, PK)
   - name: string unico (ej. Grande)
   - oz: entero (capacidad en onzas, ej. 16)
   - available: boolean default true
   - drinkPrices: relacion -> muchos DrinkPrice

3) FLAVOR (sabores/bebidas)
   - id: string (cuid, PK)
   - name: string unico (ej. Capuchino, Frutilla, Mango)
   - available: boolean default true
   - categories: relacion muchos a muchos con FlavorCategory via FlavorCategoryLink

4) FLAVORCATEGORYLINK (tabla puente sabor <-> categoria)
   - id, flavorId (FK Flavor, borrado en cascada), category (enum), createdAt
   - Unico por (flavorId, category): un sabor puede pertenecer a varias categorias

5) BOBATYPE (tipo de boba/perla)
   - id: string (cuid, PK)
   - name: string unico (ej. Tapioca, Explosivas)
   - kind: enum (TAPIOCA | POPPING)
   - available: boolean default true
   - drinkPrices: relacion -> muchos DrinkPrice

6) DRINKPRICE (matriz de precios)
   - id: string (cuid, PK)
   - category: enum (MILK | WATER | SPECIAL)
   - sizeId: FK Size (cascada)
   - bobaTypeId: FK BobaType (cascada)
   - price: entero (precio en Bs)
   - Unico por (category, sizeId, bobaTypeId): define el precio base de cada combinacion

7) TOPPING (extras)
   - id: string (cuid, PK)
   - name: string unico (ej. "Boba de tapioca extra")
   - price: entero (precio extra en Bs)
   - available: boolean default true

8) ORDER (pedido)
   - id: string (cuid, PK)
   - seq: entero unico nullable (numero de pedido correlativo visible)
   - status: enum default RECIBIDO (RECIBIDO | ACEPTADO | ENTREGADO | ANULADO)
   - customerName: string nullable (nombre del cliente, opcional)
   - deliveryType: enum nullable (MESA | LLEVAR)
   - total: entero (total a pagar en Bs)
   - createdAt: fecha default ahora
   - paidAt: fecha nullable (cuando se cobro)
   - deliveredAt: fecha nullable (cuando se entrego)
   - userId: FK User nullable (quien atiende)
   - paymentMethod: enum nullable (EFECTIVO | QR | TARJETA) - primer metodo
   - paymentMethod2: enum nullable - segundo metodo (pago dividido)
   - paymentAmount2: entero nullable - monto pagado por el segundo metodo
   - discountAmount: entero default 0
   - discountReason: string nullable
   - discountedAt: fecha nullable
   - cancelledAt, cancelReason: fecha/string nullable (anulacion)
   - delayNotified: boolean default false (si ya se aviso el retraso por Telegram)
   - items: relacion -> muchos OrderItem
   - Indices sobre (createdAt+status), (deliveredAt), (userId+status)

9) ORDERITEM (linea de un pedido)
   - id: string (cuid, PK)
   - orderId: FK Order (cascada)
   - sizeName: string (nombre copiado, no referencia viva)
   - flavorName: string
   - flavorCategory: enum
   - bobaTypeName: string
   - unitPrice: entero (precio base sin toppings)
   - quantity: entero
   - toppings: relacion -> muchos OrderItemTopping

10) ORDERITEMTOPPING (extra de una linea)
    - id: string (cuid, PK)
    - orderItemId: FK OrderItem (cascada)
    - toppingName: string
    - unitPrice: entero

11) PAYMENTCONFIG (configuracion de QR de pago)
    - id: string default "default"
    - qrImage: string (imagen base64 del QR)
    - mimeType: string
    - updatedAt: fecha

12) DAILYREPORTLOG (control de cierres diarios enviados a Telegram)
    - date: string PK (YYYY-MM-DD del dia ya cerrado)
    - sentAt: fecha

ENUMS:
- FlavorCategory: MILK (con leche) | WATER (con agua) | SPECIAL (especiales)
- BobaKind: TAPIOCA | POPPING
- OrderStatus: RECIBIDO | ACEPTADO | ENTREGADO | ANULADO
- Role: ADMIN | CAJERO
- PaymentMethod: EFECTIVO | QR | TARJETA
- DeliveryType: MESA | LLEVAR

RELACIONES CLAVE:
- User 1-N Order
- Size 1-N DrinkPrice;  BobaType 1-N DrinkPrice
- Flavor N-N FlavorCategory (via FlavorCategoryLink)
- Order 1-N OrderItem 1-N OrderItemTopping  (las lineas guardan nombres copiados, no IDs, para preservar el historico)

4. RUTAS Y PAGINAS
------------------------------------------------------------

RUTA: /login  (app/login/page.tsx)
  Pagina de inicio de sesion. Muestra el formulario LoginForm. Solo se llega aqui sin sesion.
  LoginForm (cliente): envia credenciales con signIn("credentials",...). Si falla, consulta isAccountInactive para dar un mensaje distinto si la cuenta esta desactivada. Despues valida ensureCashierRole (debe ser CAJERO o ADMIN); si no tiene rol, cierra sesion. Logrado, redirige a "/" (o callbackUrl).

RUTA: / (app/page.tsx)  [pestanas segun ?tab=...]
  Componente servidor. Exige sesion (getRequiredSession). Define el tab:
    - Sin parametro o cualquier otro -> "preparar"
    - ?tab=venta    -> "venta" (Pantalla Nueva Venta)
    - ?tab=reporte  -> "reporte" (Reporte del dia)
  Contiene el Header (logotipo "Bubba Cajero", nombre del usuario y nav con 3 enlaces).

  Tab "preparar" (Dashboard):
    Consulta los pedidos del dia actual (dayBounds de hoy) cuyo status este en
    RECIBIDO, ACEPTADO o ENTREGADO, ordenados por createdAt desc / seq desc.
    Convierte las filas a objeto Order plano (toPlainOrder) y renderiza <QueueView>.

  Tab "venta" (Nueva Venta):
    Llama getPosCatalog() (Server Action) para obtener tamanos, sabores, tipos de
    boba, matriz de precios y toppings disponibles, y renderiza <PosTerminal>.
    No usa paginacion: el catalogo llega completo por Server Action/RPC.

  Tab "reporte" (Reporte del dia):
    Llama getCashierDailyData(session.user.id) y renderiza <ReportView> con
    <ReportActions> (imprimir, PDF, enviar a Telegram).

OTRAS RUTAS:
  /api/auth/[...nextauth]  Ruta de NextAuth (handlers).
  La API es minima: todo el trabajo se hace con Server Actions y llamadas a Prisma.

5. COMPONENTES CLAVE
------------------------------------------------------------

PosTerminal (components/pos/pos-terminal.tsx) - LA PANTALLA "NUEVA VENTA"
  Props: { catalog: Catalog }
  Es la estrella del sistema. Divide la pantalla en dos columnas (70% izquierda catalogo, 30% derecha ticket).
  Estado local: activeCategory, sizeId, bobaTypeId, toppingIds[], busy, notice, error.
  - Pestañas de categoria (Especiales, Con agua, Con leche): solo se habilitan si hay al menos un sabor disponible de esa categoria.
  - Grilla de sabores: cada boton agrega la bebida al carrito con el precio calculado.
  - Selector de tamano y tipo de boba (solo items disponibles).
  - Selector de toppings (extras) con su precio.
  - Panel derecho "Ticket en curso": lista de items con cantidad (+/-), quitar, monto parcial; input de nombre de cliente opcional; selector MESA/LLEVAR; total; y boton "Enviar y Cobrar".
  - Al "Enviar y Cobrar": valida que el carrito no este vacio, llama createPosOrder(), limpia el carrito, muestra aviso "Pedido #X creado" y redirige a ?tab=preparar.
  - Calculo de precio: busca en catalog.drinkPrices la fila que coincida con (categoria activa, tamano seleccionado, tipo de boba seleccionado) -> priceOf(). El total de cada item = (unitPrice + suma de toppings) * cantidad.

PosCartStore (components/pos/pos-cart-store.ts)
  Estado global del carrito, implementado manualmente con useSyncExternalStore (no usa Redux/Zustand). Modulos: addPosItem, updatePosQuantity, removePosItem, setPosCustomerName, setPosDeliveryType, clearPosCart y hook usePosCart().
  Cada item tiene un "id" compuesto por categoria-tamano-sabor-boba-toppings ordenados, de modo que agregar la misma combinacion incrementa la cantidad en vez de duplicar la linea.
  Tipos de entrega: PosDeliveryType = "MESA" | "LLEVAR" (default MESA).
  Vive fuera del componente (modulo) para sobrevivir a cambios de ruta.

QueueView (components/queue-view.tsx) [dashboard/preparar]
  Props: { orders: Order[] }
  Muestra la cola de pedidos. Reloj interno que refresca cada 30s (antiguedad) y cada 15s hace router.refresh() (recarga servidor) mientras la pestana este visible.
  - Cluster de pedidos por estado: RECIBIDO primero, luego ACEPTADO, luego ENTREGADO.
  - Por cada pedido una OrderCard: numero (formato 00001), nombre cliente, estado, antiguedad ("Ingresado hace X" o "Entregado en X"), articulos, total, metodo de pago.
  - Para RECIBIDO: botones EFECTIVO, QR, Cobro dividido (abre SplitPaymentDialog) y Reimprimir (comanda). Al cobrar, acceptOrder pasa a ACEPTADO.
  - Para ACEPTADO: boton "Marcar entregado" (deliverOrder, con confirmacion) -> ENTREGADO.
  - Alerta Telegram: cuando un pedido en RECIBIDO/ACEPTADO supera 10 min de antiguedad, llama notifyDelayedOrder una sola vez (flag delayNotified).
  - Muestra avisos de error (modal rojo) y de exito (banner verde).

ReportView (components/report-view.tsx)
  Props: { data: CashierDailyData, myName: string }. Sin logica; despliega KPIs.

ReportActions (components/report-actions.tsx)
  Botones: Imprimir (printDailyReport), Guardar PDF (window.print), Enviar a Telegram (sendDailyReportToBot, habilitado solo desde las 23:10 hora local).

SplitPaymentDialog (components/split-payment-dialog.tsx)
  Props: { total, onConfirm(method, method2, amount2), onCancel, busy }.
  Dialogo con teclado numerico para dividir el cobro entre EFECTIVO y QR. El segundo metodo es el opuesto del primero. Validaciones: primer monto > 0, < total; segundo monto = total - primero > 0. Al confirmar llama acceptOrder(orderId, method1, method2, amount2).

6. LOGICA DE NEGOCIO CRITICA
------------------------------------------------------------

COMO SE CREA UN PEDIDO (createPosOrder, en actions/pos.ts):
  1. Exige sesion (getRequiredSession).
  2. Valida que el carrito no este vacio (items.length > 0) o lanza error.
  3. Convierte cada CartItem en OrderItem: guarda NOMBRES copiados (sizeName, flavorName, bobaTypeName), la categoria, unitPrice, quantity y sus toppings (create anidado). No guarda IDs referenciales para preservar el historico aunque el catalogo cambie.
  4. Calcula el total = sumatoria de (unitPrice + suma de precios de toppings) * quantity. Esto se recalcula en el servidor (no confia en el valor enviado).
  5. Dentro de una transaccion: calcula el proximo numero de pedido (seq = max(seq) + 1) y crea el Order con status RECIBIDO, deliveryType (MESA/LLEVAR o null), total, userId.
  6. Llama revalidatePath("/") para que la cola se actualice.
  7. Devuelve { orderId, seq, total }.

CALCULO DE PRECIO:
  - Precio base: se busca en la matriz de precios (DrinkPrice) la combinacion exacta (categoria, tamano, tipo de boba). En la UI lo hace priceOf(); en Backend se usa la funcion computeItemPrice(basePrice, toppings) = base + suma de toppings.
  - El precio unitario del item NO incluye toppings; esos se suman por separado. El total de una linea = (base + toppings) * cantidad.
  - El cliente nunca escribe el precio: siempre sale de la base de datos.

COMO FUNCIONA EL COBRO (acceptOrder, en actions/orders.ts):
  - Solo aplica a pedidos en estado RECIBIDO y no anulados.
  - Metodo de pago valido solo EFECTIVO o QR (constante AcceptablePayment; TARJETA se registra pero no es un metodo aceptable del cajero).
  - Pago simple: se registra paymentMethod y paidAt = ahora, pasa a ACEPTADO.
  - Pago dividido (opcional): method2 + amount2. Validaciones: metodo2 distinto de metodo1, ambos EFECTIVO/QR, amount2 > 0 y amount2 < total. se registran paymentMethod2 y paymentAmount2. El primer metodo cubre (total - amount2) y el segundo amount2.
  - El usuario de la orden se setea al del cajero si aun no tenia (userId).

COMO SE ENTREGA (deliverOrder, en actions/orders.ts):
  - Solo desde ACEPTADO. Si esta RECIBIDO lanza error ("aun no esta pagado"). Si ENTREGADO, error "ya fue entregado". Si ANULADO, error.
  - Pasa a ENTREGADO y fija deliveredAt (una sola vez: usa el existente si ya lo tenia).

COMO SALE LA COMANDA (impresion en lib/printing.ts + actions/printing.ts):
  - La impresora se obtiene de un archivo de configuracion compartido: ../store/printing.json (campo printerName). Si no hay impresora, error "Pide al administrador que la configure".
  - formatear comanda: texto plano de ancho 30 caracteres, con encabezado "BUBBLE DRINK", "COMANDA #XXXXX", cliente, fecha, cada item (cantidad x sabor, tamano - boba, + toppings) y TOTAL. Sin acentos (version ASCII segura para la termica).
  - La impresion usa PowerShell + System.Drawing: ajusta el tamano de letra (Consolas bold) para que la linea mas larga quepa en un rollo termico de 80mm (315 unidades de ancho). Timeout de 15s.
  - IMPORTANTE: al crear el pedido desde Nueva Venta NO se imprime automaticamente la comanda en el codigo actual. La comanda se imprime de forma MANUAL con el boton "Reimprimir" desde la cola (reprintOrder), y solo mientras el pedido siga en RECIBIDO (no aceptado).

REPORTE DIARIO (lib/report.ts):
  - Solo considera pedidos ENTREGADOS del dia (deliveredAt dentro de los limites del dia local).
  - KPIs: revenueTotal (suma total), deliveredOrders (cantidad), avgTicket (total/cantidad), avgDeliveryMinutes (promedio desde createdAt hasta deliveredAt), y desglose por metodo de pago. Para pagos divididos reparte: metodo1 recibe (total - amount2), metodo2 recibe amount2; ambos cuentan 1 pedido.
  - Rendimiento del usuario conectado (mine): filtra por userId.

ALERTA DE RETRASO (notifications.ts):
  - Un pedido en RECIBIDO/ACEPTADO con mas de 10 min dispara una notificacion en Telegram. Reclamo atomico de flag delayNotified (updateMany con condicion) para evitar duplicados entre pestanas. Si el envio falla, libera el flag para reintentar en el siguiente tick.

CIERRE DE CAJA (app/actions/report.ts + @bbspos/db daily-report):
  - sendDailyReportToBot envia el cierre del dia a Telegram, pero solo se habilita a partir de las 23:10 hora local (MANUAL_REPORT_CUTOFF). Envios anteriores lanzan error.
  - Tambien existe DAILY_REPORT_HOUR (23:20) para el cierre automatico via worker.

9. PUNTOS DE ATENCION / DEUDA TECNICA
------------------------------------------------------------

- La comanda NO se imprime automaticamente al crear una venta desde "Nueva Venta": el cajero debe presionar "Reimprimir" en la cola para sacarla en papel. Si se espera impresion automatica al cobrar, es una funcionalidad pendiente.
- La impresion depende de una configuracion externa (store/printing.json) y de Windows PowerShell + System.Drawing; no funciona en entornos Linux/servidor (tipico de entornos con impresora local conectada al cajero).
- El nombre de la impresora se lee desde la carpeta de OTRA app (store). No hay una UI en el cajero para configurarla; eso lo hace el administrador.
- Los precios, sabores, tamanos y toppings los administra el backoffice (app de admin); el cajero solo lee el catalogo con getPosCatalog(). No hay pantalla de administracion en esta app.
- El total se recalcula en el servidor (buena practica), pero no hay validacion de que el carrito enviado no haya sido manipulado para cambiar unitPrice: el servidor usa el unitPrice que viene en cada item. Idealmente el backend deberia recalcular cada unitPrice desde DrinkPrice.
- Pago "dividido": el desglose de revenue en el reporte asume que el metodo 1 cubre (total - amount2) y el metodo 2 cubre amount2. El dialog de split solo permite EFECTIVO+QR (TARJETA no aparece como metodo aceptable del cajero, aunque existe como enum).
- El numero de pedido (seq) se calcula como max(seq)+1 dentro de una transaccion. Con SQLite y unicidad en seq, no deberia haber choques, pero en alta concurrencia extrema conviene revisar.
- El catalogo se carga completo en memoria en cada apertura de la pestana venta: para catalogos muy grandes habria que paginar.
- Estado del carrito (PosCartStore) global en memoria: si el cajero recarga la pagina, el carrito se pierde (no persiste en localStorage).
- No hay sistema de devoluciones/reembolsos en el cajero: los estados solo van RECIBIDO -> ACEPTADO -> ENTREGADO (o ANULADO, aunque en el cajero no se expone boton de anulacion; eso parece venir del admin).
- El .env.example contiene un token y chat real de Telegram: si este archivo se comparte, debe rotarse el token.
- La app usa SQLite (dev/pilot); para produccion con multiples cajeros convendria migrar a PostgreSQL (el stack original lo contempla).
- No hay tests automatizados visibles en la app cajero.
