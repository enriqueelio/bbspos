## 1. Descripción General

### 1.1 Propósito

BBSPOS es un **sistema Point of Sale (POS) orientado a una cafetería de bubble tea** (negocio "BIBOSI").
Cubre la operación completa del local: catálogo y matriz de precios, toma de pedidos desde salón y
mostrador, cobro con múltiples métodos, cuenta corriente de pensionados, fidelización de clientes,
control de producción de almuerzos por jornada, arqueo de caja e impresión de comandas en
impresora térmica.

No es un e-commerce: la tienda web pública es un **kiosco de autoservicio** que arma bebidas y deja
el pedido en la cola de cocina para que el personal lo cobre en mostrador.

### 1.2 Alcance

El sistema cubre 4 terminales con permisos distintos, todo sobre **una única base de datos SQLite
compartida** por los 4 procesos Next.js. No hay microservicios, ni cola de mensajes, ni base de datos
por app.

### 1.3 Casos de uso principales

| # | Caso de uso | Actor | Terminal |

### 1.4 Terminología del negocio

| Término | Significado en el sistema |
|---|---|
| **Boba / toppings** | Insumos y extras de la bebida (tapioca, popping, shots de café, etc.) |
| **Menú del Día** | Plato de almuerzo con cantidad limitada por jornada (`LunchQuota`) |
| **Carta** | Platillos de venta libre, sin control de cantidad |
| **Ticket / comanda** | Impreso de 34 columnas que va a cocina; el ticket `#001` es el `daySeq` |
| **Caja (cartId)** | Identidad de una terminal durante la sesión, para apartar cupo de almuerzo |
| **Apartado (hold)** | Reserva temporal de unidades de almuerzo mientras están en el ticket |
| **Pensionado** | Cliente con cuenta corriente Prepago o Postpago |
| **Puntaje / puntos** | Unidad de lealtad: 1 Bs = 1 punto |

### 2.5 Migraciones

- Ubicación: `packages/db/prisma/migrations/` — **42 migraciones** aplicadas.
- Convención del proyecto: **escribir el SQL a mano** y aplicar con
  `npx prisma migrate deploy`. **Nunca** `prisma migrate dev` (es interactivo y falla en este entorno).
- `prisma generate` requiere matar todos los procesos Node que tengan el motor cargado
  (dev servers, workers) o falla con `EPERM` al renombrar `query_engine-windows.dll.node`.

## 3. Arquitectura y Estructura

### 3.1 Patrón de diseño

El sistema usa una **arquitectura modular monolítica con patrón Next.js App Router + Server Actions**,
es decir, una variante de **MVC** adaptada al framework:

| Capa MVC | Implementación en el proyecto |
|---|---|
| **Model** | Esquema Prisma (`packages/db/prisma/schema.prisma`) + lógica de dominio pura en `packages/db/src/` y `packages/types/src/` |
| **View** | Componentes React cliente (`components/*-client.tsx`, `components/pos/*.tsx`) y Server Components que solo orquestan datos |
| **Controller** | **Server Actions** (`"use server"`) y **Route Handlers** (`app/api/**/route.ts`) |

Characteristics adicionales del patrón:

1. **Capas transversales tipo *shared kernel*.** `packages/db/src/menu-day.ts` (483 líneas) y
   `packages/db/src/lunch-holds.ts` (297 líneas) contienen la lógica de negocio más delicada
   (cupos de almuerzo y apartados) y son **importadas tanto por el POS del cajero como por
   utilidades de verificación**, garantizando una única definición de la regla.
2. **Cálculos puros en `packages/types`.** `cartItemUnitTotal`, `shortCustomerName`, formatters de
   precio y labels viven fuera de los módulos `"use server"` (que solo pueden exportar funciones
   `async`, por eso los helpers client-safe están en `@bbspos/types`).
3. **UI "headless" + presentacional.** Los Server Components de cada página solo hacen el
   `fetch` de datos y renderizan un `*-client.tsx` que concentra el estado y las mutaciones.
4. **Transacciones como frontera de consistencia.** Las reglas que no pueden romperse
   (precio autoritativo, cupo de almuerzo, acumulación de lealtad, cobro de pensionado) se validan
   **dentro** de `prisma.$transaction`, no antes.

### 3.3 Convenciones estructurales del proyecto

| Convención | Detalle |
|---|---|
| **Zona horaria** | Fija `America/La_Paz` (UTC−4). En SQLite crudo: `date("createdAt"/1000,'unixepoch','-4 hours')` |
| **Numeración de pedidos** | `seq` = global y único; `daySeq` = diario (`@@unique([orderDate, daySeq])`). Visible: `daySeq ?? seq` |
| **Estados de pedido** | `RECIBIDO` → `ACEPTADO` → `ENTREGADO`, y `ANULADO` como estado final alternativo |
| **Cobro vs entrega** | Ortogonales: `paidAt` y `deliveredAt` son campos independientes |
| **Montos** | Siempre `Int` en **bolivianos (Bs)**, sin decimales. En arqueo se usa `Float` solo por herencia del modelo |
| **Nombres en tickets** | Se guardan en mayúsculas; el nombre visible es el corto (primer nombre + apellido paterno) |
| **Impresión** | Todo camino automático es *best-effort*: un fallo de impresora nunca invalida un pedido |
| **Idiomas** | Comentarios, UI y documentación en español; identificadores en inglés (`snake_case` en BD, `camelCase` en TS) |

## 4. Modelo de Datos (Esquema de BD)

**Motor:** SQLite · **ORM:** Prisma · **Archivo:** `packages/db/prisma/schema.prisma` (499 líneas)
**Total:** 24 modelos, 11 enums.

### 4.1 Entidades de usuario y acceso

| Modelo | Propósito | Campos clave |
|---|---|---|
| `User` | Personal con credenciales | `id`, `username` (unique), `name`, `password` (bcrypt), `role` (Role), `shift` (Shift), `active` |

Relaciones: `orders` (quien creó), `cancelledOrders`, `discountedOrders`, `redeemedRewards`, `cashCloses`.

### 4.2 Entidades de catálogo (bebidas)

| Modelo | Propósito | Campos clave | Restricciones |
|---|---|---|---|
| `Size` | Tamaño de vaso | `name` (unique), `oz`, `available`, `isDefault`, `imageUrl` | — |
| `Flavor` | Sabor de té | `name` (unique), `available`, `imageUrl` | — |
| `FlavorCategoryLink` | N:N sabor ↔ categoría de bebida | `flavorId`, `category` (FlavorCategory) | `@@unique([flavorId, category])` |
| `BobaType` | Tipo de perla | `name` (unique), `kind` (BobaKind), `available`, `isDefault`, `imageUrl` | — |
| `DrinkPrice` | **Matriz de precios** | `category`, `sizeId`, `bobaTypeId`, `price` | `@@unique([category, sizeId, bobaTypeId])` |
| `Topping` | Extras de bebida | `name` (unique), `price`, `available`, `imageUrl` | — |
| `AlitaSauce` | Salsas de Alitas Mixtas | `name` (unique), `available` | — |

> **Punto clave:** el precio de una bebida **no** se guarda en el producto sino en la matriz
> `DrinkPrice` (combinación categoría × tamaño × boba). El topping se suma por ítem.

### 4.3 Entidades de catálogo (platillos)

| Modelo | Propósito | Campos clave | Restricciones |
|---|---|---|---|
| `MenuItem` | Platillo de carta o almuerzo | `name`, `category` (MenuCategory), `price`, `description`, `available`, `enMenuDelDia`, `menuDelDiaDate`, `isMixtas`, `requiredSauces` | `@@index([category, available])` |
| `MenuItemOption` | Variante de precio obligatoria (p. ej. Milanesa Pollo/Res) | `menuItemId`, `name`, `price`, `requiredSauces` | `@@unique([menuItemId, name])` |

`MenuCategory` (17 valores): `ALMUERZO`, `SANDWICH`, `PANINI`, `ENSALADA`, `PIQUEO`, `COMPARTIR`,
`ALITA`, `HAMBURGUESA`, `MILANESA`, `LOMO`, `POLLO`, `KIDS`, `POSTRE`, `WAFFLE`, `PANCAKE`,
`EXTRAS`, `BEBIDA`.

### 4.4 Entidades de cliente y lealtad

| Modelo | Propósito | Campos clave |
|---|---|---|
| `Customer` | Cliente frecuente **y** pensionado (misma fila) | `name`, `ci`, `phone` (**unique, nullable**), `pensionType`, `balance`, `creditLimit`, `totalVisits`, `totalSpent`, `lastVisitAt`, `points` |
| `CustomerBenefitRule` | Regla de nivel configurable | `name`, `description`, `metric` (BenefitMetric), `threshold`, `active` |
| `CustomerReward` | Bitácora de otorgos y canjes | `customerId`, `ruleId?`, `type` (OTORGADO/CANJE), `pointsUsed`, `description`, `redeemedById?`, `orderId?` |
| `CustomerLedger` | Movimientos de la cuenta corriente | `customerId`, `type` (RECARGA/PAGO_DEUDA/CONSUMO), `amount`, `paymentMethod?`, `orderId?` |

**Semántica de saldo:** `balance > 0` = saldo a favor (Prepago); `balance < 0` = deuda (Postpago).
`creditLimit` limita la deuda (0 = sin límite).

**Índice único en `phone`:** en SQLite los `NULL` no chocan entre sí, así que puede haber
varios clientes sin teléfono. La validación de duplicado se hace en la capa de aplicación
(`assertPhoneAvailable`) para dar un error de negocio legible en vez del `P2002` crudo de Prisma.

### 4.5 Entidades de venta

| Modelo | Propósito | Campos clave |
|---|---|---|
| `Order` | Cabecera de pedido | `seq` (unique, global), `orderDate`, `daySeq`, `status`, `customerName`, `customerId?`, `deliveryType?`, `notes`, `total`, `discountAmount`, `discountReason`, `paymentMethod?`, `paymentMethod2?`, `paymentAmount2?`, `createdAt`, `acceptedAt`, `paidAt`, `deliveredAt`, `cancelledAt`, `cancelReason`, `deliveredAt`, `tiempoEstimado`, `scheduledFor?`, `reservationConfirmed`, `reserveLeadMin`, `delayNotified` |
| `OrderItem` | Línea de pedido (bebida **o** platillo) | `orderId`, `sizeName?`, `flavorName?`, `flavorCategory?`, `bobaTypeName?`, `menuItemName?`, `menuItemCategory?`, `menuItemOptionName?`, `menuItemDetail?`, `unitPrice`, `quantity`, `tiempoProduccion` |
| `OrderItemTopping` | Topping de una línea | `orderItemId`, `toppingName`, `unitPrice` |

> **Diseño clave:** `OrderItem` guarda una **instantánea de nombres y precios**
> (`sizeName`, `flavorName`, `unitPrice`, …), no los `id`. El historial de pedidos es inmutable
> aunque el catálogo cambie después. La contrapartida es que el conteo de almuerzos vendidos
> se hace por **nombre de plato** (`menuItemName`), no por `menuItemId`.

Restricciones de `Order`:

```prisma
seq   Int? @unique                 // numeración global
@@unique([orderDate, daySeq])      // ticket visible único por día
@@index([createdAt])
@@index([createdAt, status])
@@index([status, createdAt])
@@index([deliveredAt])
@@index([userId])
@@index([userId, status])
@@index([customerId])
```

### 4.6 Entidades de producción (almuerzos)

| Modelo | Propósito | Campos clave |
|---|---|---|
| `LunchQuota` | Cantidad diaria de un plato del Menú del Día | `menuItemId`, `date` (YYYY-MM-DD local), `planned` (**nullable** = no programado), `lowThreshold` (default 5) |
| `LunchAdjust` | Bitácora de correcciones manuales | `quotaId`, `delta`, `note`, `userId` |
| `LunchHold` | Apartado de cupo por caja | `menuItemId`, `date`, `cartId`, `quantity`, `expiresAt` |

Restricciones: `@@unique([menuItemId, date])` en `LunchQuota`;
`@@unique([menuItemId, date, cartId])` en `LunchHold`.

> **El vendido NO se guarda.** Se deriva de los pedidos no anulados de la jornada, de modo que
> `remaining = planned + Σ LunchAdjust.delta − sold − holdsAjenos` nunca se desincroniza y
> **anular un pedido restituye las unidades solo**.

## 5. Módulos y Lógica de Negocio

### 5.1 Inventario y control de stock

#### 5.1.1 Qué existe y qué NO existe

| Nivel de control | Implementado | Mecanismo |
|---|---|---|
| Disponibilidad de catálogo | Sí | Flags booleanos `available` en `Size`, `Flavor`, `BobaType`, `Topping`, `MenuItem` |
| Cantidad diaria de almuerzos | Sí | `LunchQuota` + `LunchAdjust` + `LunchHold` |
| Stock de insumos (té, perlas, jarabes) | **No** | No existen modelos de compras, entradas, merma ni proveedores |
| Costeo de insumos / margen | **No** | No hay `cost` en ningún modelo |
| Proveedores / compras | **No** | — |

#### 5.1.2 Cálculo del cupo disponible

`packages/db/src/menu-day.ts:185-253` — `lunchStockRows()`:

```ts
// planned + Σ ajustes − sold − heldOthers
const delta = quota.adjusts.reduce((acc, a) => acc + a.delta, 0);
const available = (quota.planned ?? 0) + delta - sold - heldOthers;

rows.set(target.id, {
  planned: quota.planned,
  sold,
  held: heldTotal,
  heldByMe: heldMine,
  // Sin cantidad asignada no hay control: `remaining` queda null y el terminal
  // bloquea la tarjeta hasta que alguien asigne unidades.
  remaining: quota.planned == null ? null : available,
  lowThreshold: quota.lowThreshold,
});
```

Conceptos:

| Concepto | Definición |
|---|---|
| `sold` | Unidades en `OrderItem` de pedidos **no anulados** de la jornada. Reservas cuentan en `scheduledFor`, el resto en `createdAt` |
| `held` | Total de apartados vigentes de la jornada |
| `heldByMe` | Apartados vigentes de la caja que consulta (`excludeCartId`) |
| `heldOthers` | `held − heldByMe`: lo que **sí** te quita disponibilidad |
| `remaining` | `planned + Σ delta − sold − heldOthers`, o `null` si no hay cantidad programada |

> **Regla clave:** el `remaining` de una caja **excluye sus propios apartados**, así que el número
> no baja cuando el cajero suma líneas a su propio ticket, pero baja en el acto en que otra caja
> se lleva unidades. En `apps/cajero/lib/lunch-stock.ts:12-18` la UI muestra
> `addableUnits = remaining − heldByMe`.

#### 5.1.3 Apartado por caja (`LunchHold`)

`packages/db/src/lunch-holds.ts` implementa la regla **"el primero que agarró el plato gana"**.
El carrito vive en el navegador, así que el clic en la tarjeta debe dejar una reserva en la BD.

| Constante | Valor | Ubicación |
|---|---|---|
| `HOLD_TTL_MIN` | 20 minutos | `menu-day.ts:34` |
| `RENEW_WINDOW_MIN` | 6 minutos (umbral de renovación) | `lunch-holds.ts:24` |

| Función | Propósito |
|---|---|
| `acquireLunchHold(cartId, menuItemId, qty)` | Puerta de entrada al agregar al ticket. Transacción: calcula `free = remaining − myHeld` y falla con **3 mensajes distintos** según el motivo (todo apartado propio / se lo llevó otra caja / alcanza para algunas) |
| `releaseLunchHold(cartId, menuItemId, qty)` | Devuelve unidades al común; borra la fila si llega a 0 |
| `releaseCartLunchHolds(cartId)` | Libera todos los apartados de la caja (limpiar ticket) |
| `touchCartLunchHolds(cartId)` | Renueva los apartados propios. La ejecuta el poll del catálogo (cada 15 s) |
| `reconcileCartLunchHolds(cartId, lines)` | Al reabrir el POS: ajusta los apartados a las líneas reales del carrito y devuelve `lost[]` con los platos que otra caja se llevó |
| `consumeCartLunchHolds(db, cartId)` | Al guardar el pedido: borra los apartados (las unidades pasan a `sold`). **Se llama dentro de la transacción del pedido** |
| `assertLunchCapacity(db, cartId, demand, date, excludeOrderId?)` | Última barrera antes de guardar. Lanza `LunchCapacityError` con mensaje para el cajero |

**Identidad de caja:** `cartId` se genera en el navegador
(`localStorage` key `bbspos-pos-cart-id`) y se refleja en una cookie espejo
(`bbspos_pos_cart_id`, `apps/cajero/lib/cart-id.ts`) para poder leerla desde el servidor.

#### 5.1.4 Ajustes y bitácora

`adjustLunchStockForDay()` (`menu-day.ts:315-356`):
- Si el plato **no tiene** cuota y el delta es **positivo** → la reposición **es** la base
  (`planned = delta`, sin fila de ajuste), para no contarla dos veces.
- Si el delta es **negativo** sin cuota → error `"Primero suma unidades para poder restar."`
- Con cuota existente → crea fila en `LunchAdjust` con `delta`, `note`, `userId`.

`requireTodayMenuItem()` (`menu-day.ts:266-278`) **rechaza** cualquier plato que no sea del
Menú del Día de hoy, para que nadie toque el cupo de otra jornada.

#### 5.1.5 Alertas de stock bajo y retraso

`packages/db/src/telegram-alert.ts` + `scripts/telegram-alert-worker.ts` (poll cada 15 s):

| Alerta | Condición | Anti-duplicado |
|---|---|---|
| Pedido retrasado | Tiempo real > `tiempoEstimado` + margen | `Order.delayNotified` (se libera al cobrar) |
| Stock bajo de almuerzo | `remaining <= lowThreshold` | Marca en el propio pedido/notificación |

#### 5.2.2 Cálculo de precio: **autoritativo en POS, confiado en el store**

Este es el punto más importante del flujo y la diferencia crítica entre apps.

**POS del cajero — precio recalculado desde BD** (`apps/cajero/actions/pos.ts:141-243`,
`pricePosItems`). Ignora por completo `item.unitPrice` del cliente:

```ts
// Bebida: precio de la matriz DrinkPrice por combinación
const base = drinkPriceByCombo.get(`${item.category}|${item.size.id}|${item.bobaType.id}`);
if (base === undefined) throw new Error("COMBINACION_NO_DISPONIBLE");

// Toppings: precio leído de BD, nunca el que envía el cliente
const dbTopping = toppingById.get(t.id);
if (!dbTopping || dbTopping.price <= 0) throw new Error("PRECIO_INVALIDO");

// Platillo: precio de la variante (MenuItemOption) o del producto base
const unitPrice = item.optionId
  ? optionById.get(item.optionId)?.price
  : menuItemById.get(item.menuItemId)?.price;

// Tiempo estimado = el del producto que MÁS tarda (no la suma)
const tiempoEstimado = items.reduce((max, item) => Math.max(max, productionMinutesFor(item)), 0);
```

**Tienda web — precio confiado al cliente** (`apps/store/app/actions/order.ts:34,41,49-52`):
usa `item.unitPrice` y `t.price` enviados por el navegador y calcula el total con ellos.
Sin sesión, sin rate limit. **Es una vulnerabilidad conocida** (ver §7.3).

#### 5.2.3 Cálculo de impuestos y descuentos

| Concepto | Implementación |
|---|---|
| **Impuestos** | **No existen.** Bolivia no aplica IVA a este tipo de operación y el sistema no modela impuestos |
| **Descuentos** | Solo a nivel de pedido y **exclusivo del Admin**: `Order.discountAmount`, `discountReason`, `discountedAt`, `discountedById` (`apps/admin/app/actions/orders.ts:174`). Acumula: `applyDiscount` suma al `discountAmount` existente |
| **Total** | `Order.total` es el total bruto del carrito. El descuento **no** se resta del `total`, se reporta aparte y se descuenta al computar el neto en reportes |

#### 5.2.4 Creación del pedido POS — `createPosOrder`

`apps/cajero/actions/pos.ts:297-469`. Secuencia:

1. **Validaciones de sesión y entrada** (`pos.ts:307-319`): carrito no vacío, nombre obligatorio, `deliveryType` válido.
2. **Reserva normalizada** (`pos.ts:247-263`): ISO → `Date`; `reserveLeadMin >= 1`, default 30.
3. **Cliente** (`pos.ts:329-337`): si hay `customerId` debe existir; texto libre sin coincidencia → **invitado** (`customerId: null`).
4. **Usuario de sesión verificado** (`pos.ts:341-344`): si fue borrado tras el login, el pedido queda sin `userId` (evita violación de FK `P2003`).
5. **Transacción única** (`pos.ts:354-404`):
   - `assertLunchCapacity` **dentro** de la transacción (sin ventana entre control y guardado)
   - Asignación de `seq` y `daySeq` con `max + 1`
   - `order.create` con items anidados
   - `consumeCartLunchHolds`: lo apartado pasa a vendido
6. **Fuera de la transacción:** `revalidatePath("/")` e impresión *best-effort*.

```ts
// Numeración dentro de la transacción
const order = await prisma.$transaction(async (tx) => {
  await assertLunchCapacity(tx, cartId, lunchDemand, date);

  const first = await tx.order.findFirst({ orderBy: { seq: "desc" }, select: { seq: true } });
  const seq = (first?.seq ?? 0) + 1;
  const last = await tx.order.findFirst({
    where: { orderDate }, orderBy: { daySeq: "desc" }, select: { daySeq: true },
  });
  const daySeq = (last?.daySeq ?? 0) + 1;

  const created = await tx.order.create({ data: { /* ... */ } });
  await consumeCartLunchHolds(tx, cartId);   // lo apartado pasa a vendido
  return created;
});
```

> **Riesgo conocido:** `max + 1` sin bloqueo explícito puede colisionar con dos escrituras
> concurrentes. En ese caso salta la restricción única y el error se traduce a
> `"No se pudo crear el pedido"` (`pos.ts:405-411`).

`updatePosOrder` (`pos.ts:477-604`) edita **solo reservas sin confirmar**. Rechaza si no hay
`scheduledFor`, si está confirmada, cobrada, anulada o entregada (`pos.ts:517-527`). Excluye el
propio pedido del `sold` para no contarlo dos veces y **no imprime** (la comanda sale al cobrar).

#### 5.2.5 Ciclo de vida del pedido

```text
   store/web                POS cajero / POS mesero
       │                            │
       ▼                            ▼
   RECIBIDO ──────► (acceptQueueOrder) ──► ACEPTADO ──► ENTREGADO
       │                            │           (deliveredAt)
       │                            │
       └──────────── ANULADO ◄──────┴───────────┘
                  (cancelledAt + cancelReason + canceledById)
```

| Transición | Acción | Notas |
|---|---|---|
| `null → RECIBIDO` | `createOrder` (store) | Default del schema |
| `null → ACEPTADO` | `createPosOrder` / mesero | El POS crea directo "pendiente de cobro" |
| `RECIBIDO → ACEPTADO` | `acceptQueueOrder` (cajero) | Arranca `acceptedAt` = timer de producción |
| `RECIBIDO/ACEPTADO/ENTREGADO → cobro` | `acceptOrder` | **Cobro y entrega son ortogonales:** si venía de `RECIBIDO` cambia a `ACEPTADO`; si ya estaba `ACEPTADO`/`ENTREGADO` conserva estado y solo registra el pago |
| `ACEPTADO → ENTREGADO` | `deliverOrder` | `deliveredAt` se escribe una sola vez |
| `→ ANULADO` | `cancelReservation` / `cancelOrder` | Desde la cola solo si **no** está cobrado; si ya se cobró, delega en Admin |

#### 5.2.6 Procesamiento de pago

`apps/cajero/app/actions/orders.ts`:

| Método | Descripción |
|---|---|
| `acceptOrder(orderId, method, method2?, amount2?)` | Pago normal. Soporta **pago dividido**: `total − paymentAmount2` con el primer método, `paymentAmount2` con el segundo. Idempotente: `paidAt` solo se escribe una vez |
| `acceptPensionOrder(orderId, customerId)` | Cobra contra la cuenta del pensionado con `paymentMethod = PENSION` |

Ambos **bloquean el rol `MESERO`** y **acumulan lealtad en la misma transacción** que registra `paidAt`:

```ts
// apps/cajero/app/actions/orders.ts:265-267
if (order.customerId) {
  await accumulateCustomerLoyalty(tx, order.customerId, order.total, paidAt);
}
```

```ts
// apps/cajero/app/actions/customers.ts:203-218
export async function accumulateCustomerLoyalty(
  tx: Prisma.TransactionClient, customerId: string, total: number, when: Date,
): Promise<void> {
  await tx.customer.update({
    where: { id: customerId },
    data: {
      totalVisits: { increment: 1 },
      totalSpent:  { increment: total },
      points:      { increment: total },   // 1 Bs = 1 punto
      lastVisitAt: when,
    },
  });
}
```

> **Idempotencia:** al escribirse `paidAt` una sola vez, la lealtad se acumula exactamente
> una vez por pedido.

#### 5.2.7 Cobra contra cuenta de pensionado

`acceptPensionOrder` (`orders.ts:285-400`):

| Modalidad | Regla |
|---|---|
| **Prepago** | Exige `balance >= total`; si no, sugiere la recarga exacta que falta (`orders.ts:324-330`) |
| **Postpago** | Permite deuda, pero rechaza si `nextBalance < −creditLimit` cuando hay límite configurado (`orders.ts:331-338`) |

En transacción: actualiza `balance`, crea `CustomerLedger` tipo `CONSUMO` con `orderId`,
registra el cobro y acumula lealtad. **El dinero no entra a la caja de ese turno.**

#### 5.2.8 Reservas

Modelo: `scheduledFor`, `reservationConfirmed`, `reserveLeadMin` (default 30).

| Característica | Comportamiento |
|---|---|
| Cola | Vive en la pestaña **RESERVAS** sin arrancar el reloj de producción |
| Impresión | **No** imprime al crearse; imprime al confirmar (cobro) o con `confirmReservation` |
| Aviso | La card se ilumina `reserveLeadMin` minutos antes de la hora pactada |
| Edición | Solo mientras no esté confirmada, cobrada, anulada ni entregada |
| Confirmación sin cobro | `confirmReservation(orderId)` → `ACEPTADO` + `reservationConfirmed = true` + comanda diferida |
| Cupo de almuerzo | Cuenta en la fecha pactada (`scheduledFor`), no en la de creación |

### 5.3 Cierres de Caja

#### 5.3.1 Denominaciones soportadas

`200, 100, 50, 20, 10, 5, 2, 1, 0.5` Bs (`packages/types/src/index.ts:817-827`).

#### 5.3.2 arqueo: flujo

1. **`getCashCloseStats(date)`** (`apps/cajero/lib/cash-close.ts:10-37`) contrasta
   los pedidos **entregados** del día + los movimientos del ledger de pensionados.
2. **`confirmCashClose({denominations, notes})`** (`app/actions/cash-close.ts:21-50`):
   - Bloquea rol `MESERO`
   - **Recalcula el total en el servidor**, nunca confía en el formulario
   - Valida que las denominaciones sean válidas, no repetidas y con cantidades enteras ≥ 0
   - Nota limitada a 300 caracteres
3. **`printCashClose(closeId)`** reimprime el ticket del cierre con `formatCashCloseText()`.

#### 5.3.3 Modelo contable del arqueo

| Campo | Significado |
|---|---|
| `denominations` | JSON `[["200",2],["100",3],…]` — desglose del efectivo contado |
| `countedCash` | `Σ valor × cantidad` (físico) |
| `systemCash` | Efectivo esperado por el sistema (**ya incluye** `rechargeCash`) |
| `systemQr` / `systemCard` | Esperado por QR y por tarjeta |
| `pensionSales` | Consumos del día cobrados a cuenta de pensionados → **NO entran a la caja** |
| `rechargeCash` / `rechargeQr` | Recargas y pagos de deuda del día → **SÍ entran a la caja** |
| `diffCash` | `countedCash − systemCash` → sobrante (+) / faltante (−) |

> Los pagos divididos ya vienen **prorrateados** entre sus métodos antes de contrastar
> (`total − paymentAmount2` / `paymentAmount2`).

#### 5.3.4 Turnos y múltiples cierres

El enum `Shift` (`MANANA`, `TARDE`, `SIN_TURNO`) se guarda en `User`, pero
`CashClose` admite **varios cierres por día** (p. ej. turno de mañana y de tarde), cada uno
con `closedAt`, `userId` y `denominations` propios → historial auditable y reimprimible.

### 5.5 Clientes, lealtad y cuenta corriente

#### 5.5.1 Resolución del cliente en el POS

`apps/cajero/app/actions/customers.ts`:

| Acción | Comportamiento |
|---|---|
| `getCustomerSuggestions(term)` | Autocompletado: `contains` por `name` o `phone`, tope 8, `lastVisitAt` desc |
| `linkCustomerByText(text)` | **Vincula sin crear.** Si el texto parece teléfono (`PHONE_RE`) busca `phone` exacto; si no, `name` exacto case-insensitive. Devuelve `null` → **venta invitado** |
| `registerCustomerAtPos({name, phone?})` | Alta explícita. **Prohíbe `MESERO`.** Nombre obligatorio en mayúsculas, teléfono opcional y único, con error claro ante duplicado |
| `getCustomerLoyalty(customerId)` | Vista de lealtad + `levelName` según reglas activas |
| `shortCustomerName(customer)` | Helper **derivado** en `@bbspos/types`: primer nombre + apellido paterno (`"MARIA FERNANDEZ LOPEZ"` → `"MARIA FERNANDEZ"`) |

> **Decisión de diseño:** el POS **nunca crea clientes automáticamente**. Sin coincidencia, la
> venta queda como invitado (`customerId: null`). El alta es una acción explícita del cajero.
> Esto evita llenar la base con duplicados de nombres tecleados rápido en hora punta.

#### 5.5.2 Niveles de lealtad

`levelNameOf()` (`customers.ts:20-56`) evalúa las reglas activas contra:

| Métrica | Valor comparado |
|---|---|
| `SPEND_MONTH` | `Σ Order.total` del mes actual (pagados, no anulados) |
| `VISITS_MONTH` | `count` de pedidos del mes actual |
| `POINTS` | `Customer.points` acumulado histórico |

Inicio de mes local = medianoche La Paz = `04:00 UTC`
(`new Date(Date.UTC(y, m-1, 1, 4, 0, 0))`, `customers.ts:32`).

#### 5.5.3 Admin: ranking y canje

`apps/admin/app/actions/loyalty.ts`:

| Acción | Detalle |
|---|---|
| `getCustomerRanking(periodo, search?)` | Top 10 por `Σ total` sobre `Order.paidAt` no nulo. Periodos: `MONTH`, `DAYS_30`, histórico. `search` filtra por nombre/teléfono |
| `redeemCustomerPoints({customerId, points, ...})` | Valida saldo (`"Saldo insuficiente: X tiene N puntos y solicitaste M."`), decrementa `points` y crea `CustomerReward` tipo `CANJE` en la **misma transacción** |
| `listBenefitRules()` / `saveBenefitRule(...)` | CRUD de reglas de nivel |

> **Guardas de robustez** en `redeemCustomerPoints`: verifica que el usuario de sesión exista
> en BD antes de escribir `redeemedById` (evita violación de FK `P2003` si la cuenta fue
> eliminada tras el login).

### 7.4 Cumplimiento de OpenSpec (SDD)

El proyecto usa **OpenSpec** para specs/changes antes de codificar:

```text
openspec/
├── config.yaml
├── changes/                       # cambios en curso
│   ├── 2026-09-22-add-customer-loyalty/     # implementado, falta verificar
│   └── controlar-creacion-clientes/         # implementado, falta verificar
└── archive/                       # cambios archivados
```

Cada change tiene `proposal.md`, `design.md`, `tasks.md` y `specs/<capability>/spec.md`
(especificaciones en formato SHALL/MUST). Un change se archiva al completarse la implementación
y la verificación.

## 8. Apéndices

### 8.1 Glosario técnico

| Término | Significado en este proyecto |
|---|---|
| **Server Action** | Función `async` marcada con `"use server"`; se ejecuta en el servidor pero se invoca como una RPC desde el cliente |
| **Route Handler** | `app/api/**/route.ts` con `export async function GET/POST/PUT/DELETE` |
| **Server Component** | Componente React que corre en el servidor; puede ser `async` y consultar la BD directamente |
| **`after()`** | API de Next.js 15 para ejecutar código **después** de enviar la respuesta (usada para impresión) |
| **`prisma.$transaction(async (tx) => …)`** | Transacción interactiva; recibe `tx` con el mismo API que `prisma` |
| **CVA** | Class Variance Authority: variantes de estilo tipadas (p. ej. `statusVariants.ts` para estados de pedido) |
| **TTL** | Time To Live; aquí, la vida de un `LunchHold` (20 min) |
| **`@unique` en SQLite** | Los valores `NULL` **no** se consideran duplicados entre sí → varios clientes sin teléfono pueden convivir |
| **`P2003` / `P2002`** | Códigos de error de Prisma: violación de foreign key / violación de constraint único |
