2.2 MAPA DE RELACIONES
-----------------------
User 1──→N Order            (via userId — quien creo/ato el pedido)
User 1──→N Order            (via canceledById — quien anulo, @relation "OrderCanceledBy")
User 1──→N Order            (via discountedById — quien desconto, @relation "OrderDiscountedBy")
Size 1──→N DrinkPrice       (via sizeId, onDelete Cascade)
BobaType 1──→N DrinkPrice   (via bobaTypeId, onDelete Cascade)
Order 1──→N OrderItem       (via orderId, onDelete Cascade)
OrderItem 1──→N OrderItemTopping (via orderItemId, onDelete Cascade)
Flavor M──→N FlavorCategory (via FlavorCategoryLink pivote, @@unique)
MenuItem ── sin FK a pedidos; se copia a OrderItem.menuItemName/menuItemCategory

Patron de desnormalizacion:
  OrderItem almacena sizeName, flavorName, flavorCategory, bobaTypeName,
  menuItemName y menuItemCategory como strings (snapshot del catalogo al momento
  del pedido, NO como FK). Esto garantiza precios/inventario historico inmutable
  aunque el catalogo cambie despues.
  OrderItemTopping almacena toppingName como string (NO FK a Topping).

2.3 FLUJO DE VENTAS (ciclo de vida de una Order)
--------------------------------------------------
1. Creacion:
   - Venta publica (apps/store): el cliente arma la bebida en el builder,
     confirma el pedido; se crea Order con status=RECIBIDO.
   - Venta manual (POS): cajero/mesero arman el ticket en el terminal
     (bebidas configurables + platos del Menu del Dia); mesero envia a caja
     con tipo MESA forzado; cajero/admin puede Enviar y Cobrar.
2. RECIBIDO  : comanda impresa esperando en caja (impresion termica best-effort).
   - El cajero registra el pago (EFECTIVO | QR | pago dividido) -> ACEPTADO,
     registrando metodo, fecha (paidAt) y responsable (userId).
3. ACEPTADO  : pago registrado por el cajero.
   - Entrega las bebidas (deliverOrder) -> ENTREGADO, registrando deliveredAt.
4. ENTREGADO : bebidas entregadas al cliente. Sin acciones posteriores.
Transicion terminal ANULADO: desde cualquier estado, con motivo (cancelReason) y
canceledBy. Un pedido anulado no puede avanzar a otro estado.
Secuencia obligatoria: RECIBIDO -> ACEPTADO -> ENTREGADO, sin retrocesos ni
saltos (la entrega de un RECIBIDO sin pago es rechazada).

Motivo de la cadena de estados (historial):
  - Inicialmente 2 estados (INGRESADO/ENTREGADO).
  - Con cobro en caja se introdujo RECIBIDO -> ACEPTADO (tres estados) que es
    la secuencia vigente en el codigo y el schema.

4.1 LOGICA DE ZONA HORARIA (America/La_Paz)
-------------------------------------------
Zona horaria: America/La_Paz (UTC-4 fijo, SIN horario de verano)
Ni moment.js, ni date-fns, ni luxon — solo Intl.DateTimeFormat nativo

Constantes:
  packages/types/src/index.ts:
    BUSINESS_TIME_ZONE = "America/La_Paz"
    MANUAL_REPORT_CUTOFF = "23:10"
    MANUAL_REPORT_CUTOFF_MINUTES = 23 * 60 + 10

Helpers principales:
  packages/db/src/daily-report.ts:
    - zonedDateKey(date)       -> "YYYY-MM-DD" en America/La_Paz
    - zonedMinutes(date)       -> minutos del dia en la zona
    - shiftDayKey(date)        -> dia clave segun turno (manana/tarde)
    - targetReportDate()       -> fecha objetivo del reporte
  apps/admin/lib/reports/range.ts:
    - REPORT_TIMEZONE, tzOffsetMs (-4h)
    - getZonedParts, zonedToUtc, dayBounds, rangeBounds
    - dayKeyOf ("YYYY-MM-DD"), monthKeyOf ("YYYY-MM"), isoWeekKeyOf
    - hourOfDay, weekdayIndex
  apps/cajero/lib/day.ts:
    - TIME_ZONE, localDayKey, todayKey, zonedStartOfDay, dayBounds
  packages/types/src/index.ts:
    - zonedClockMinutes(date, tz) -> minutos del dia

Funcionamiento:
  - Las fechas se almacenan en UTC (Prisma DateTime en SQLite)
  - Todas las queries de reportes/cola usan dayBounds() para filtrar el dia
    local [start UTC, end UTC]
  - El Menu del Dia usa zonedDateKey() como clave de vigencia: el plato activo
    "hoy" deja de serlo al cambiar la fecha en La Paz, sin workers

4.2 IMPRESION TERMICA
---------------------
Mecanismo: PowerShell + System.Drawing.PrintDocument (Windows-only, NO escpos)
No hay paquete npm de impresion — nativo via spawn de powershell.exe

Configuracion compartida:
  apps/store/printing.json (gitignored) — { "printerName": "..." }
  Todas las apps leen ese archivo (printText renuncia a ESC/POS):
    store:  join(process.cwd(), "printing.json")
    cajero/mesero/admin: join(process.cwd(), "..", "store", "printing.json")

Nucleo (printText):
  1. getPrinterName() lee printing.json
  2. runPowerShell(script) — timeout 15s, powershell.exe -NoProfile
  3. Base64-encode UTF-8, auto-dimensiona fuente Consolas 12pt bold
     (Max(Min) según ancho), papel ~80mm (300-340 unidades)
  4. toAscii(text) — elimina acentos (á→a, ñ→n) por compatibilidad termica

Formato de comanda:
  Header "BUBBLE DRINK" + "COMANDA #seq", 34 columnas
  Abreviaturas: Grande→G, Extragrande→XG, Tapioca→Tap, Explosivas→Expl
  Lineas de almuerzo se imprimen como "Qty x MenuItem" (columna propia)
  Fecha es-BO con dateStyle/timeStyle

Gestion de impresora (admin):
  connectSharedPrinter(uncPath), listPrinters (Win32_Printer), setPrinterConfig,
  formatTestPage — API routes /api/printer, /api/printer/connect, /api/printer/test
  UI: apps/admin/(dashboard)/printer/page.tsx

Donde se imprime (best-effort, non-blocking):
  Store (crear pedido), Cajero y Mesero (crear pedido POS), reimpresion desde
  cola cajero/mesero y admin, reporte diario del cajero, resumen/cierre admin

4.3 CIERRE DIARIO AUTOMATICO A TELEGRAM
---------------------------------------
Mecanismo: 2 workers Node.js con loop setInterval(60s) en el contenedor Docker
No hay cron del SO — todo corre dentro del container

A. REPORTE DIARIO DE CIERRE
  Fuente: packages/db/src/daily-report.ts
  Worker: packages/db/scripts/daily-report-worker.ts

  collectReportStats(key):
    - Ingresos de pedidos entregados + ticket promedio + desglose por metodo
      (incluye splits: total-amount2 para method1, amount2 para method2)
    - Tiempo promedio de entrega (deliveredAt - createdAt)
    - Hora pico, perdidas (anulaciones, descuentos), desglose por categoria
      (incluye plata de ALMUERZO con etiqueta compartida)
  buildReportMessage(key, stats): markdown "CIERRE DIARIO BIBOSI" con
    secciones FINANZAS / OPERACION / FUGAS Y ALERTAS en Bs
  sendDailyReportToTelegram(key):
    - Verifica DailyReportLog (anti-duplicado), POST a Telegram, persiste log
  Worker loop: intervalo 60s, calcula fecha objetivo (hoy si paso
    DAILY_REPORT_HOUR, si no dia anterior — recupera dias caidos del container),
    flags --date=YYYY-MM-DD y --dry-run

  Triggers manuales (habilitados despues de 23:10 / MANUAL_REPORT_CUTOFF):
    - Cajero: apps/cajero/app/actions/report.ts (boton "Enviar a Telegram")
    - Admin: apps/admin/app/actions/daily-report.ts (boton "Cierre diario")
    - Gating: zonedClockMinutes >= MANUAL_REPORT_CUTOFF_MINUTES

B. ALERTA DE PEDIDOS ATRASADOS
  Fuente: packages/db/src/telegram-alert.ts
  Worker: packages/db/scripts/telegram-alert-worker.ts

  checkDelayedOrders():
    - Query: delayNotified=false, paidAt=null, hace > DELAY_ALERT_MINUTES y
      (ACEPTADO sin entregar O ENTREGADO sin pagar -> "caja leak")
    - Anti-spam atomico via updateMany (solo un worker envia)
    - Si falla Telegram, resetea delayNotified=false para reintento
  sendAlert(seq, name, minutes, status): markdown "PEDIDO ATRASADO"
  Worker loop: 60s, flag --once

  Configuracion:
    DAILY_REPORT_HOUR = "23:20" / MANUAL_REPORT_HOUR = "23:10"
    DELAY_ALERT_MINUTES = "10"
